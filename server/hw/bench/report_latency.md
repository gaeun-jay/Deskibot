# 음성 파이프라인 지연 최적화 기록

> 측정일 2026-08-19 · ESP32 실기기 + EC2(deskibot-osaka)
> STT 엔진 비교(`report.md`)와 별개 작업이다. 결론부터: **지연 문제는 STT가 아니었다.**

## 1. 출발점 — STT는 병목이 아니다

지연 단축이 목표라면 어디를 고쳐야 하는지부터 재야 했다.
서버 로그 9건(실사용)의 단계별 소요:

| 단계 | 시간 | 비중 |
|---|---|---|
| STT | 0.97초 | 25% |
| **LLM (Claude)** | **2.37초** | **61%** |
| TTS | 0.53초 | 14% |
| 합계(서버) | 3.87초 | |

STT 엔진 교체로 얻는 0.16초는 서버 처리의 4%에 불과하다.

## 2. 진짜 병목은 전송이었다

서버 내부만 계측돼 있어 전송 구간이 안 보였다. 응답 헤더로 서버 처리 시간을
내려보내고(`X-Server-Time`), 기기가 `왕복 − 서버 = 네트워크`를 계산하게 했다.

첫 실측(16-bit PCM, 일괄 전송):

| | 업로드 | 서버 처리 | 네트워크 | 본문 수신 | 총 체감 |
|---|---|---|---|---|---|
| #2 | 199 KB | 4.31초 | **6.58초** | 0.92초 | **11.86초** |
| #3 | 231 KB | 4.44초 | **6.36초** | 6.70초 | **17.54초** |

**네트워크가 서버 처리보다 크다.** 업로드 실효속도는 24~36 KB/s인데
오디오는 초당 32 KB로 쌓인다 — **7초 말하면 업로드에 또 7초가 걸린다.**

## 3. 적용: µ-law 8-bit 전송

16-bit PCM(32 KB/s) → G.711 µ-law(16 KB/s). 손실 압축이라 인식률 손실을
**기존 90발화 데이터셋으로 먼저 실측**하고 채택했다.

| 엔진 | 원본 CER | µ-law CER | 차이 | 판정 |
|---|---|---|---|---|
| google_v1 | 0.0896 | 0.0820 | −0.0076 | 유의차 없음 |
| clova_csr | 0.0774 | 0.0785 | +0.0011 | 유의차 없음 |

조건별로도 악화가 없었다. 우려했던 원거리(1 m, 피크 830~1,500)에서 오히려
양쪽 다 미세하게 나아졌다 — µ-law는 로그 압신이라 작은 진폭에서도 SNR을
유지한다(검증: 피크 400에서도 SNR 34 dB). 전사가 달라진 건 180건 중 19건이고,
원본은 인식됐는데 µ-law에서 빈 결과가 된 경우는 0건이었다.

**결과**: 업로드 199 KB → 97 KB, 네트워크 6.58초 → **4.02초 (39% 단축)**.

구현: 기기가 `X-Audio-Encoding: mulaw` 헤더와 함께 보내고 서버가 되돌린다.
헤더가 없으면 기존 PCM16으로 처리하므로 **구형 펌웨어와 호환된다.**
STT 엔진 선택과도 무관하다.

## 4. 보류: 스트리밍 업로드

녹음이 끝난 뒤 통째로 올리는 대신 **녹음과 동시에** 흘려보내는 방식.
구현을 마치고 동작을 확인했다.

**성과**: 체감 12.4초 → **8.59초**. 업로드 대기가 사실상 사라졌다.

```
[UP] 전송 완료: 67840 bytes µ-law (4.2초)   ← 녹음과 동시 진행
[LAT] 응답 대기 : 6.19s (서버 처리 4.14s)
[LAT] 본문 수신 : 2.34s
[LATENCY] ⏱ 8.59초
```

**그런데 껐다.** 메모리가 감당하지 못했다.

| | 정상 | 스트리밍 켰을 때 |
|---|---|---|
| 연속 내부 블록 | 32,756 B | **24,564 B** |
| 결과 | 정상 | TLS 연결 실패, WebSocket 끊김 |

WebSocket + HTTPClient에 **세 번째 TLS 컨텍스트**를 얹은 것이 한계를 넘겼다.
`main.cpp`의 `[Diag]` 주석이 경고하던 그대로 — 총 힙보다 연속 블록이 먼저 마른다.

`VOICE_STREAM_UPLOAD 0`으로 두면 관련 코드가 통째로 컴파일에서 빠진다.
구현은 `src/screens/voice.h`에 그대로 남겨 뒀다.

### 되살리려면 메모리부터

1. **음성 중에는 WebSocket을 끊기** (가장 현실적) — 집중 세션용이라 음성 명령과
   동시에 필요한 경우가 드물다. TLS 컨텍스트가 둘로 준다.
2. 폴백용 HTTPClient 경로 제거 — 안전장치를 포기하는 트레이드오프
3. 업로더 스택·버퍼를 PSRAM으로 — TLS 컨텍스트 자체는 내부 RAM이라 근본 해결은 아님

### 구현 중 만난 함정 (되살릴 때 주의)

- **중복 실행 위험**: 스트리밍이 실패했다고 일괄 전송으로 폴백하면, 서버가 이미
  처리한 요청을 한 번 더 실행한다. 실제로 발생했다(nginx 499 + 서버 로그 2회 처리).
  `add_todo`였다면 할 일이 두 개 생겼을 것이다.
  → 종료 청크 전에 끊겼을 때만 재전송하도록 `UP_RETRY_SAFE` / `UP_SPENT`로 분리했다.
- **응답 대기**: `readStringUntil`은 Stream 타임아웃에 기대면 서버가 응답하기도 전에
  빈 문자열을 반환한다. 서버가 3~6초 걸리므로 `available()`을 직접 기다려야 한다.
- **UI 프리즈**: TLS 핸드셰이크를 버튼 콜백에서 하면 UI 스레드가 0.5~1초 멈춰
  터치가 씹힌다. 반드시 업로더 태스크에서 연결할 것.
- **머리 트림 기준점**: 연결에 걸리는 시간 동안 녹음된 발화를 무음으로 오인하면
  안 된다. '지금 위치'가 아니라 '신호가 처음 잡힌 위치'를 기준으로 삼는다.

## 5. 남은 지연 (다음 작업 후보)

현재(µ-law 일괄 전송) 체감 약 9~11초의 구성:

| 구간 | 시간 | 개선 수단 |
|---|---|---|
| 업로드/네트워크 | 4.0~4.7초 | 스트리밍 업로드(메모리 확보 후) |
| 서버 처리 | 3.2~3.9초 | LLM 응답 길이(2.3~2.6초가 LLM) |
| 응답 오디오 수신 | 0.8~2.3초 | TTS 스트리밍 재생 |

**TTS 스트리밍 재생**이 다음 후보로 좋다. 지금은 오디오를 전부 받은 뒤 재생을
시작하는데, 앞부분부터 재생하면 체감이 크게 달라진다. 재생 경로만 건드리므로
업로드 쪽과 격리되고, 실패해도 소리가 끊기는 정도다.
**LLM 응답을 짧게 하는 것이 가장 싸지만**(LLM 시간과 TTS 크기가 함께 준다),
제품 요구상 응답 길이는 줄이지 않기로 했다.

## 6. 부수 발견 — 원거리 발화가 잘린다

`voice.h`의 무음 제거 문턱이 `max(TRIM_ABS_FLOOR=600, peak/12)`인데, 1 m 거리에서
발화 피크가 830~1,500까지 떨어지면 600이 항상 이겨 조용한 끝음절이 잘려 나간다
(u24-c3 끝 진폭 310, u26-c3 490). 같은 문장의 30 cm 녹음은 피크 4,650으로 멀쩡하다.

벤치 공정성에는 영향이 없지만(같은 wav를 두 엔진에 전달), **실사용에서 멀리서
말하면 말끝이 사라진다.** 문턱을 절대값이 아니라 피크 비례로 바꾸는 것이 맞다.

## 7. 계측 방법

기기가 구간을 나눠 찍는다. 서버가 응답 헤더로 자기 처리 시간을 알려주므로
`왕복 − 서버 = 네트워크`가 계산된다.

```
[LAT]   업로드 크기 : 62720 bytes µ-law (3.9초 오디오)
[LAT]   POST 왕복   : 8.62s
[LAT]   ├ 서버 처리 : 3.94s  (stt=0.778,llm=2.582,tts=0.579)
[LAT]   └ 네트워크  : 4.68s
[LAT]   본문 수신   : 2.14s
[LATENCY] ⏱ 녹음 종료 → 스피커 출력: 10.82초
```

관측 도구는 `bench/` 밖에 두지 않았다 — 시리얼을 그대로 보면 된다.
