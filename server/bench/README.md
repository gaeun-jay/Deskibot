# STT 엔진 비교 벤치마크 (Google vs CLOVA)

현행 운영 구성인 Google Cloud Speech v1을 기준선으로 두고, CLOVA STT가
한국어 음성 명령에서 더 나은지 검증한다. 결과로 `report.md`를 채워
채택 여부를 결정한다.

---

## 1. 왜 CER만 보면 안 되는가

파이프라인은 `STT → Claude tool use → action JSON`이다. 최종 사용자가
겪는 실패는 "글자가 틀린 것"이 아니라 "명령이 잘못 해석된 것"이다.

실제로 드라이런에서 같은 발화의 전사 결과가 CER 0.056 ~ 0.167로 3배 벌어졌는데
intent는 셋 다 정답이었다. 호출어를 "데스 키보드"로 잘못 들어도 add_todo는
정상 동작했기 때문이다. 반대로 "뽀모도로"가 "포모도로"가 되면 CER은 0.125에
불과하지만 명령은 실패한다.

그래서 지표를 두 층으로 나눈다.

| 층 | 지표 | 역할 |
|---|---|---|
| 1차 (텍스트) | **CER** 주지표, WER 보조, 빈 결과율 | 왜 틀렸는지 진단 |
| 2차 (E2E) | **intent 정확도** (도구 + 핵심 인자 일치) | **채택 결정 근거** |
| 운영 | 레이턴시 p50/p95, 비용 | 유의차 없을 때 결정 |
| 도메인 | 고유명사 12개 인식률 | 힌트 기능 비교 |

한국어는 띄어쓰기·조사 변동이 커서 WER이 과하게 나쁘게 나온다. 드라이런에서도
표기만 다른 문장이 CER 0.0 / WER 0.75로 갈렸다. **CER(공백 제거)을 주지표로 쓴다.**

## 2. 공정성 통제 — 여기서 대부분의 비교가 망가진다

1. **같은 wav 하나를 모든 엔진에 먹인다.** 엔진마다 따로 녹음하면 비교 자체가 무효다.
2. **힌트를 끄고 맨몸으로 비교한다.** 현행 Google은 `phrase hints + boost 15.0`으로
   도메인 튜닝된 상태인데, CLOVA CSR에는 부스팅 기능 자체가 없다. 튜닝된 Google과
   맨몸 CLOVA를 비교하면 엔진 성능이 아니라 "튜닝을 했는가"를 재게 된다.
   → **비교 대상은 `google_v1:0`과 `clova_csr:0` 두 구성뿐이다.**
   `run_bench.py --no-hints`로 힌트 셀 자체를 돌지 않는다.
3. **부스팅 비교가 필요해지면** CLOVA Speech(장문 API, `X-CLOVASPEECH-API-KEY` +
   invoke URL) 구독이 있어야 대등해진다. 지금 범위 밖이다.
4. **EC2에서 돌린다.** 로컬(집 회선)에서 재면 국내 CLOVA가 부당하게 유리해진다.
   레이턴시는 반드시 운영 서버와 같은 위치에서 측정한다.
5. **판정 기준을 데이터 보기 전에 못박는다.** 아래 6절 참고.
6. **LLM 조건을 고정한다.** intent 채점은 카테고리 목록과 "현재 시각"을 상수로
   박아 둔다(`intent.py`의 `CATEGORIES`, `FIXED_NOW`). DB 상태나 실행일이
   결과를 흔들면 엔진 비교가 오염된다.

## 3. 데이터셋 — 실기기로 녹음해야 한다

노트북 마이크로 녹음하면 ESP32 마이크 특성·거리·게인이 빠져서 현장 성능과
무관한 숫자가 나온다. 서버에 덤프 스위치를 넣어 뒀다.

```bash
DEBUG_DUMP_AUDIO=1 DUMP_ONLY=1 venv/bin/python server.py
```

**`DUMP_ONLY=1`을 반드시 같이 켠다.** 이게 없으면 STT→LLM→DB까지 그대로 실행돼서
"치과 예약 삭제해줘", "영어 숙제 다 했어" 같은 발화가 **실제 할 일 데이터를
바꿔 버린다**(할 일 21개 추가 + 삭제·완료 실행). 켜면 오디오만 저장하고
STT/LLM/TTS를 전부 건너뛰므로 DB도 안전하고 API 비용도 0이다.

기기에는 0.15초짜리 확인음이 돌아간다. ESP는 오디오 길이가 0이면 에러로
처리하기 때문에(`src/screens/voice.h:441`) 빈 응답 대신 톤을 생성해서 보낸다.
"삑" 소리가 나면 저장된 것이다.

조건 하나씩 끊어서 진행한다.

```bash
# 1) 대본 출력 — 이 순서대로 말한다
python3 bench/label_audio.py --cond c1 --script

# 2) 20발화를 다 말한 뒤, 이름 붙이기 미리보기
python3 bench/label_audio.py --cond c1

# 3) 맞으면 적용
python3 bench/label_audio.py --cond c1 --apply
```

파일명이 타임스탬프라 정렬 순서 = 녹음 순서다. 그래서 **한 발화라도 빠지거나
재녹음이 섞이면 그 뒤가 전부 밀린다.** 조건 하나(20발화)를 끝낼 때마다 바로
이름을 붙이고, 개수가 안 맞는다는 경고가 뜨면 그 자리에서 바로잡는다.
c1 → c2 → c3 순으로 세 번 반복한다.

**설계: 30발화 × 3조건 = 90녹음 (완전 짝지음)**

| 조건 | 소음 | 거리 |
|---|---|---|
| c1 | 조용 | 30 cm |
| c2 | 생활소음 | 30 cm |
| c3 | 조용 | 100 cm |

> **c3 해석 주의 — 기기 트리밍이 말끝을 자른다.**
> `voice.h:485`의 무음 제거 문턱이 `max(TRIM_ABS_FLOOR=600, peak/12)`인데,
> 1 m 거리에서는 발화 피크가 830~1,500까지 떨어져 `peak/12`(약 90)가 무력해지고
> 600이 항상 이긴다. 그 결과 조용한 끝음절이 문턱 아래로 내려가 통째로 잘린다.
> 실측: u24-c3의 끝 진폭 310, u26-c3은 490 — 둘 다 600 미만이라
> "지워줘", "준비 끝냈어"가 사라졌다. 같은 문장의 c1 녹음은 피크 4,650으로 멀쩡하다.
>
> 두 엔진에 **같은 wav**가 들어가므로 엔진 비교의 공정성은 유지된다. 다만 c3 수치는
> "거리 1 m의 순수 효과"가 아니라 **"1 m + 트리밍 손실"** 로 읽어야 한다.
> 트리밍 문턱은 절대값이 아니라 피크에 비례해야 맞다 — STT 결론과 별개인
> 펌웨어 이슈로 남겨 둔다.

같은 발화가 세 조건에 모두 있어야 조건별 비교와 쌍(paired) 검정이 동시에 된다.
단일 요청 20발화(조회 4 / 추가 7 / 완료 4 / 삭제 3 / 기기명령 2)에
**복합 요청 10발화**(한 문장에 도구를 두 번 부르는 경우)를 더했다.
`데스키봇`·`뽀모도로`·`마감` 같은 도메인 어휘를 섞었다.

복합 발화는 서버 정책과도 맞물린다 — 추가는 한 요청에 3건까지,
완료·삭제도 3건까지 처리한다(`MAX_ADDS_PER_REQUEST`,
`MAX_MUTATIONS_PER_REQUEST`). intent 채점은 실행 결과가 아니라
**LLM이 도구를 몇 번, 어떤 인자로 불렀는가**를 본다.

기기명령 2건(`뽀모도로 시작해줘` 등)은 LLM 도구가 아니라 `ref_tool=none`이다.
STT 오인식이 엉뚱한 도구를 부르는 **오탐(false command)** 을 잡는 역할이다.

## 4. 실행

```bash
venv/bin/pip install -r bench/requirements.txt

# 1) 전사 — 같은 wav를 모든 엔진 × 힌트 셀에 통과
venv/bin/python bench/run_bench.py --engines google_v1,clova_csr --no-hints --repeat 3

# 2) intent 채점 (읽기 전용 — DB를 건드리지 않는다)
venv/bin/python bench/intent.py

# 3) 지표 + 유의성 검정
venv/bin/python bench/score.py --baseline google_v1:1 --challenger clova_csr:0

# 4) 그래프 5종
venv/bin/python bench/plot.py --baseline google_v1:1 --challenger clova_csr:0
```

`run_bench.py`는 이미 끝난 조합을 건너뛰므로 중간에 죽어도 이어서 돌릴 수 있다.
`--repeat`은 레이턴시용이고 중앙값을 취한다(네트워크 변동이 크다).

> **DB 안전**: `server.run_llm()`은 `_run_tool()`로 실제 DB를 변경한다
> (`add_todo`는 INSERT). `intent.py`는 이걸 부르지 않고 `voice_prompt`만 가져다
> 도구 **선택**만 보고 실행은 하지 않는다. 운영 데이터에 영향이 없다.

### 엔진별 필요한 환경변수

| 엔진 | 변수 | 상태 |
|---|---|---|
| `google_v1` | `GOOGLE_API_KEY` | ✅ `.env`에 있음 |
| `clova_csr` | `NAVER_API_KEY`, `NAVER_CLIENT_ID` | ✅ 있음 (`.env`는 `NAVER_CLLIENT_ID` 오타지만 어댑터가 둘 다 읽는다) |
| `google_v2` | `GCP_PROJECT_ID`, `GOOGLE_APPLICATION_CREDENTIALS` | ⬜ 미설정 (API 키 불가, 서비스 계정 필요) |
| `clova_speech` | `CLOVA_SPEECH_INVOKE_URL`, `CLOVA_SPEECH_SECRET` | ⬜ 미설정 (별도 구독) |

자격증명이 없는 엔진은 자동으로 건너뛰고 이유를 출력한다.

**`google_v2`(chirp_2)를 꼭 후보에 넣을 것.** 이걸 빼고 비교하면 "Google이 진 게
아니라 Google v1이 진 것"일 수 있다. 엔진 교체보다 API 버전을 올리는 쪽이 훨씬
싼 개선이므로, 여기서 이기면 결론이 바뀐다.

## 6. 판정 기준 (측정 전에 확정)

데이터를 보고 기준을 만들면 편향이다. 순서대로 적용한다.

1. **intent 정확도** 차이가 McNemar 검정에서 유의(p < 0.05)하면 → 높은 쪽 채택.
2. 유의차가 없으면 → **p95 레이턴시**가 유의하게 낮은 쪽.
3. 그것도 비슷하면 → **현행 유지**(google_v1). 교체에는 코드·운영 리스크가
   따르므로 동점이면 바꾸지 않는다.
4. 어떤 경우든 **빈 결과율**이 5%를 넘는 엔진은 탈락. 사용자에게 "음성이
   인식되지 않았습니다"가 20번에 한 번 나오면 체감 품질이 무너진다.

n=60에서 3%p 차이는 우연일 수 있다. **"유의차 없음"도 정당한 결론**이고,
그 경우 위 2~3번으로 내려간다.

## 7. 통계

- **CER**: 발화별 쌍 부트스트랩(10,000회, seed 42) → 평균 차이의 95% 신뢰구간.
  CI가 0을 포함하면 유의차 없음.
- **intent**: McNemar 정확검정. 불일치 쌍(한쪽만 맞힌 발화)만 본다.
  scipy 없이 정확 이항검정으로 계산한다.

## 8. 정규화 규칙 (보고서에 반드시 명시)

`normalize.py`. 엔진마다 표기 습관이 달라서, 정규화 없이는 성능이 아니라
표기 차이를 재게 된다.

- 문장부호 제거 (Google은 `enable_automatic_punctuation=True`라 마침표가 붙는다)
- 소문자화, NFC 정규화
- 한국어 수사 → 아라비아 숫자, **단위 앞에서만** ("세 시" → "3시").
  "세탁"·"한글" 같은 무관한 단어를 건드리지 않기 위한 제한이다.
- CER은 공백 제거 후 계산, WER은 공백 유지
